# Código con Codex y Ollama local (P20)

`codex-local-v1` conserva Codex CLI **0.166.0**, el sandbox y los informes E8/E9. Cambia el proveedor de inferencia a Ollama local mediante una pasarela del controlador. El motor ejecuta herramientas reales dentro del contenedor; el servidor local solo produce mensajes y llamadas estructuradas. [P19](local-specialists.md) conserva su motor de texto sin shell `local-readonly-v1`.

## Configuración y uso

1. Prepara explícitamente Ollama **0.13.4 o posterior** y un modelo ya instalado que anuncie `completion` y `tools`. FerWeb no instala pesos, inicia Ollama ni elige un modelo. Desactiva la nube del servidor y limita su exposición según [ai.md](ai.md#ollama-del-anfitrión-desde-docker).
2. Usa [codex.local.example.json](codex.local.example.json) como referencia para el archivo privado `secrets/codex.json`, o la ubicación privada indicada por `FERWEB_CODEX_CONFIG_FILE`. Sustituye el nombre de ejemplo por el identificador instalado y permitido. `apiKey: null` y `models: []` permiten este recorrido sin clave OpenAI. Si ya tienes configuración API, conserva sus valores y añade `local`. No copies secretos a documentación o Git.
3. Ejecuta `npm run docker:up`, o `npm run docker:restart` después de cambiar un archivo privado ya montado. Solo `runner` recibe esta configuración. La URL admite HTTP hacia `localhost`, `127.0.0.1`, `host.docker.internal` u `ollama`, sin ruta, credenciales, query ni redirecciones. Dentro de Docker, localhost es el propio controlador; para Ollama en Windows se usa `host.docker.internal` y la conectividad/firewall descritos en la guía de IA. No se reduce la verificación TLS de otros destinos.
4. En un proyecto activo con tarea y snapshot GitHub sincronizado, abre **Trabajos → Nueva tarea con Codex → Destino de inferencia Codex → Ollama local**. Elige modelo, perfil, rol compatible y límites. El catálogo local tiene su propia disponibilidad y no depende de una clave API. Si no hay modelo con revisión y herramientas confirmadas, no se admite el trabajo.
5. Ejecuta y abre el informe común: proveedor, CLI, modelo solicitado/reportado, digest observado, huella de configuración, comandos, diff, controles y pruebas independientes. **Detener Codex** conserva el recorrido de cancelación. Revisa los cambios antes de usar E9; guardar revisión y publicar una PR son acciones separadas. GitHub mantiene sus permisos y política de red propios.

En **Agentes → Equipos y plantillas**, la política **Codex con Ollama local** guarda `inferenceMode: local-coding-only`. Preparar, aprobar e iniciar conservan esa política para todas las etapas, incluidos revisores y reunión final. Los perfiles Node, TypeScript/React y especialistas de solo lectura reutilizan sus imágenes y controles existentes. Cada etapa hereda su modelo del plan; seleccionar modelos locales distintos por rol sigue siendo una capacidad del recorrido P19. No hay enrutamiento mixto o fallback cloud automático.

La repetición E9 conserva el destino nativo. Los revisores por dimensiones de un trabajo local requieren también una plantilla local; una plantilla cloud se rechaza. Esto conserva la frontera de inferencia, sin convertir GitHub ni toda la aplicación en servicios offline.

## Decisión de integración y protocolo

Se comprobó dentro de la imagen fijada que `codex --help` ofrece `--oss` y `--local-provider` con Ollama/LM Studio. La documentación oficial describe [Codex con proveedor personalizado](https://docs.ollama.com/integrations/codex), [Responses de Ollama](https://docs.ollama.com/api/openai-compatibility) y el [ciclo oficial del agente](https://openai.com/index/unrolling-the-codex-agent-loop/). Responses se introdujo en Ollama 0.13.3; FerWeb exige 0.13.4 como mínimo conservador para este recorrido. La consulta de versión/capacidades acredita compatibilidad anunciada, no calidad del modelo.

Se reutiliza el ciclo de Codex mediante un proveedor Responses configurado por FerWeb. La CLI solo conoce la pasarela loopback de su ejecución. El controlador consulta `/api/version`, `/api/tags` y `/api/show`, y envía generaciones exclusivamente a `/v1/responses` del destino permitido. No usa un endpoint directo del anfitrión desde el código, gestión de modelos, autenticación del escritorio o mecanismos de descarga. Los nombres con `cloud` y metadatos remotos conocidos quedan excluidos. El operador sigue siendo responsable de que el servidor de confianza no derive inferencias a otro destino.

Las solicitudes son stateless: se transmite el historial acotado del trabajo, sin referencias a conversaciones/respuestas externas. Solo se anuncian las funciones `exec_command` y `write_stdin` con esquemas cerrados. Se validan nombres, argumentos, tamaños, sesión y límites de espera/salida; no se permiten herramientas alojadas, búsqueda web, MCP, delegación o parámetros para elevar permisos. El contenedor conserva UID 1000, red `none`, raíz de lectura, workspace temporal, ausencia de secretos y socket Docker, plazos, cuotas y verificación independiente de P11/P12. [Frontera de confianza y límites](codex.md#límites-efectivos).

La pasarela recibe SSE con un máximo de 4 MB y comprueba una terminación completa, herramientas, identificadores y coherencia entre deltas y resultado. Reconstruye los eventos a partir del resultado validado antes de entregarlos a Codex: no promete mostrar cada token mientras Ollama lo genera. Una llamada desconocida, argumentos inválidos, historial fabricado, identificador repetido, flujo incompleto o excesivo cierran la inferencia de ese trabajo. La repetición de la misma herramienta/argumentos sin una nueva salida observable también se detiene; se ignoran identificadores de chunk y tiempos variables. Esta detección es una heurística de progreso observable, reforzada por los máximos existentes de peticiones y tiempo.

El catálogo, digest y huella se comprueban antes de iniciar y de generar. Un cambio invalida las condiciones sin seleccionar otro modelo. El digest es una observación del servidor; no demuestra que un alias no cambiara durante la inferencia. Cerrar la conexión y parar el sandbox no confirma que Ollama haya detenido su cómputo remoto: `remoteCancellationConfirmed` permanece desconocido. Los tokens solo se conservan cuando hay uso observado del proveedor; si falta, siguen desconocidos, sin convertir contadores inferidos de CLI en mediciones reales.

## Persistencia, contexto y aceptación

La migración aditiva **028** valida la selección y revisión del modelo local en la configuración de los trabajos existentes `codex-v1`. El nuevo identificador distingue la inferencia; no duplica la cola, informes o publicación. Se mantienen autorización por proyecto, archivo, revocación, generación/lease, idempotencia, presupuestos y ausencia de reintento automático de código. Los informes históricos siguen válidos sin los metadatos nuevos.

Los paquetes P10 pueden prepararse con `executionId: codex-local-v1`, con sus recibos e invalidación. Selección y ranking son deterministas; los embeddings existentes siguen siendo locales. No se invocan resumidores, selectores ni jueces cloud como auxiliares. Código, skills, memoria y entregas son datos sin autoridad para ampliar permisos.

La aceptación automatizada usa HTTP Ollama simulado, CLI y herramientas reales dentro de Docker, SQL y verificador independiente. Cubre corrección de un defecto, informes/revisión E9, equipo secuencial, requisitos y cambios de catálogo, bucles, respuestas inválidas, cancelación, timeout, egress y aislamiento. Chromium recorre la selección local, ejecución, diff, revisión y móvil. [Evidencia ejecutada](status.md).

La inferencia real requiere un modelo y hardware elegidos y autorizados. En un proyecto de prueba autorizado, registra versión de Ollama, identificador/digest, recursos disponibles, commit/tarea, límites, trabajo e informe. Comprueba una corrección pequeña, uso de herramientas, pruebas independientes y cancelación, manteniendo desactivada la nube y sin publicar automáticamente. Compara calidad y tiempos solo con mediciones de esas ejecuciones; no se acredita equivalencia con OpenAI, ahorro, velocidad ni GPU mediante los dobles de prueba. Docker comparte kernel y el controlador sigue siendo privilegiado.
